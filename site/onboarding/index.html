Onboarding for utviklere

Alt du trenger for å komme fra tom maskin til en kjørende, prefylt legeerklæring — og videre til å bidra: lokalt miljø, koden, testing, fallgruver og en liste over gode første oppgaver.

Siden er skrevet for deg som kan .NET og har sett Altinn Studio, men ikke nødvendigvis SMART on FHIR eller norsk helse-IT.

Mål

Velkommen — dette skal du ha etter første uke

Denne siden er for deg som skal arbeide videre med initiativet: bygge, teste eller forvalte. Den forutsetter at du kan .NET og har sett Altinn Studio før, men ikke at du kan SMART on FHIR eller norsk helse-IT.

  • Du forstår hva prosjektet påstår, og hva som er bevist versus bare tegnet (Status).
  • Du har hele den lokale kjeden oppe: Altinn localtest, en FHIR-mock, en EPJ-simulator og én av Altinn-appene — og har trykket deg gjennom en prefylt, signert legeerklæring.
  • Du har kjørt SMART-launchen mot en ekte, ekstern SMART-server og sett hva som skjer når noe går galt.
  • Du vet hvor hemmeligheter bor (og at de aldri bor i repoet).
  • Du har valgt en første oppgave fra listen nederst.

Vær ærlig om hva dette er

Dette er et proof of concept. Tokenvalidering, issuer-allowlist, distribuert sesjon og Altinn-pålogging i produksjon er ikke på plass, og det finnes ingen automatiserte tester. Det er ikke feil du skal skamme deg over å finne — det er arbeidslisten (risikoregisteret).

Første kjøring

Få hele kjeden opp lokalt

Fire ting må kjøre samtidig: Altinn localtest (med PDF og lastbalanserer), HAPI FHIR som EPJ-mock, SMART-mocken og selve Altinn-appen.

Kjent hull: app-localtest må endres, og endringene ligger ikke i repoet

Prosjektet forutsetter en modifisert klone av app-localtest som i dag bare finnes lokalt hos en utvikler. Uten endringene starter ikke kjeden. Å sjekke inn dette som en patch (slik local-dev/nav-epj-testing/nav-epj-local-fixes.patch allerede gjør for nav-epj) er en god første oppgave — se listen nederst.

1. Hosts-fil

Legg til denne linjen i C:\Windows\System32\drivers\etc\hosts (krever administrator):

127.0.0.1  local.altinn.cloud

2. Endre app-localtest (tre ting)

  1. Legg til HAPI FHIR som en tjeneste i compose-filen din: 
      hapi_fhir:
    container_name: hapi-fhir
    image: hapiproject/hapi:latest
    restart: always
    networks:
      - altinntestlocal_network
    ports:
      - "8080:8080"
    environment:
      - hapi.fhir.fhir_version=R4
      - hapi.fhir.allow_multiple_delete=true
      - hapi.fhir.reuse_cached_search_results_millis=-1
  2. Bevar porten i Host-headeren. I loadbalancer/templates/nginx.conf.conf: bytt proxy_set_header Host $host; til proxy_set_header Host $http_host;. $host utelater porten, og da bygger appen SMART-callbacken uten port (ERR_CONNECTION_REFUSED). Start lastbalansereren på nytt etterpå.
  3. Kjør appen i HTTP-modus. Sett LocalPlatformSettings:LocalAppMode = "http" og LocalAppUrl til adressen appen kan nås på fra containerne (port 5005). Hvilken adresse som virker avhenger av oppsettet ditt — host.docker.internal, host.containers.internal eller verts-IP-en til WSL/Podman.

3. Start containerne

PowerShell 
podman machine start        # hvis Podman-maskinen står
$env:ALTINN3LOCAL_PORT = "8000"
# Start compose-prosjektet i app-localtest (Podman Desktop → Compose → Start)

Dette gir localtest-loadbalancer (nginx, port 8000), localtest (Altinn Platform, 5101), localtest-pdf3 (PDF, 5300) og hapi-fhir (8080).

4. Last inn testdata

PowerShell 
cd local-dev
.\seed.ps1

Oppretter syntetiske FHIR-ressurser: legen Ola Nordmann (HPR 1234567) ved Sandvika Legesenter, seks pasienter med konsultasjoner, og for kjeveortopedisk-caset tannlegen Tina Tannlege, Sentrum Tannklinikk og pasienten Kaja Kviss. De fem første pasientenes fødselsnumre er oppdiktede og består ikke MOD11-kontroll; pasienten Høy Hai har et ekte, Tenor-verifisert syntetisk nummer og brukes mot eksterne NHN-miljøer der personen faktisk må eksistere.

5. Start SMART-mocken

PowerShell 
cd local-dev\smart-mock
npm install
node server.js        # lytter på http://localhost:9090

6. Start Altinn-appen

PowerShell 
cd src\App
dotnet run            # lytter på http://localhost:5005

Gi containerne litt tid før du tester. Rekkefølgen som har virket er: containere, SMART-mock, så appen — og localtest kan henge hvis plattformen får forespørsler før appen er oppe.

7. Åpne EPJ-simulatoren

Gå til http://localhost:9090/epj, velg en pasient og trykk:

  • Hurtigstart — logger deg inn som Dr. Ola Nordmann og åpner skjemaet med FHIR-prefill. Bruk denne først.
  • Start i Altinn — den fulle SMART EHR Launch-flyten med OAuth-redirect.

Hurtigstart bruker /smart/dev-login, som bare finnes i Development: appen henter en JWT fra localtest server-til-server, setter Altinn-cookiene og seeder FHIR-sesjonen. Du kan også gå rett til http://local.altinn.cloud:8000/digdir/forer-legeerklaering/smart/dev-login.

Case 2

Kjør kjeveortopedisk-appen

Samme kjede, annen app. Bare én app kan være koblet til localtest på port 5005 om gangen — stopp førerrett-appen først.

PowerShell 
cd src\AppKjeveortopedisk
dotnet run

Åpne http://local.altinn.cloud:8000/digdir/kjeveortopedisk-henvisning/smart/dev-login. Appen starter som Tina Tannlege og åpner med pasienten Kaja Kviss.

Testbrukere: localtest leser appens wwwroot/testData.json og lar den erstatte standardbrukerne helt — den slås ikke sammen med dem, og cachen er global. Derfor inneholder kjeveortopedisk-appens fil også de vanlige testbrukerne (Ola Nordmann m.fl.). Mangler en vanlig testbruker, er det trolig fordi appens testData.json ikke har dem — ikke fordi noe er slettet.

Testing

Teste SMART-flyten mot noe som ikke er vår egen mock

SMART-mocken beviser bare at appen snakker med seg selv. For å finne ekte feil må du teste mot en standardkompatibel server.

  • launch.smarthealthit.org er en offentlig SMART-sandkasse. local-dev/smarthealthit-testing/test-smart-launch.ps1 reproduserer alle ni «Simulated Error»-variantene automatisk. Nøkkelen er å forhåndsvelge nøyaktig én pasient og én behandler i launch-payloaden — da hopper launcheren over den interaktive velgeren. Alt står i docs/TESTGUIDE-SMARTHEALTHIT.md.
  • nav-epj er NAVs EPJ-simulator, som kan settes opp lokalt som et Norge-tilpasset testmiljø med riktige fødselsnummer- og HPR-OID-er. Det trengs en patch og kjente bugs må rettes — se docs/NAV-EPJ-TESTMILJO.md.
  • Epic on FHIR er relevant fordi Helseplattformen kjører Epic, men sandkassen er foreløpig blokkert — se docs/EPIC-TESTMILJO.md.

Browser-pane med annonseblokkering

Hvis du tester skjemaet i en innebygd nettleser med innholdsblokkering, kan kall som /api/v1/footer blokkeres (ERR_BLOCKED_BY_CLIENT) og siden se ødelagt ut uten at appen er feil. Bekreft med curl mot api/layouts/form og api/v1/texts/nb før du leter i koden.

Sikkerhet

Hemmeligheter: aldri i repoet

Standing regel: private nøkler, klienthemmeligheter og tokens limes aldri inn i en chat, en issue eller en commit. De lagres i filer utenfor repoet eller i brukerhemmeligheter.

PowerShell 
cd src\App
dotnet user-secrets init      # kun første gang
dotnet user-secrets set "SmartOnFhir:ClientSecret" "<verdi>"
  • App-konfig går i dotnet user-secrets, som lagres under %APPDATA%\Microsoft\UserSecrets\ — utenfor repoet.
  • private_key_jwt-nøkler genereres med generate-client-assertion-jwk.ps1 og skrives til en mappe utenfor repoet; appen får bare stien (SmartOnFhir:ClientAssertionPrivateKeyPath).
  • HelseID-nøkkelen for Helsenorge-testene refereres via miljøvariabelen HELSEID_JWK_PATH.
  • Restart appen etter hver user-secrets-endring; en kjørende prosess har allerede lest konfigurasjonen.
Pasientsiden

Teste mot Helsenorge

De fire flytene på Helsenorge-siden er små konsollprosjekter under local-dev/helsenorge-*-test. For å kjøre dem trenger du fire ting:

  1. En klient registrert i HelseIDs selvbetjening for test, med private_key_jwt og scopene nhn:helsenorge.eksternapi/oppgave og …/skjema. Klienten er multi-tenant.
  2. Den private nøkkelen som en lokal fil, referert via HELSEID_JWK_PATH.
  3. En IP-adresse NHN har åpnet. Portalen avviser alt annet med «ikke gjenkjenner ip-adressen din». Fungerer det ikke hjemmefra, bruk VPN eller be om at adressen åpnes.
  4. En testperson som har fullført samtykket på portalen (nivå «Full»). Ellers får du «ikke digitalt aktiv».

Portalen nås med https://tjenester.hn2.test.nhn.no/?pnr=<fnr> for en syntetisk testperson; oppgavene ligger under «Oppgaver».

Fallgruver

Det vi allerede har trådt i

Lokalt miljø

  • Hosts-filen: uten local.altinn.cloud får du ingen svar fra localtest.
  • Host-headeren: $host i nginx utelater porten og ødelegger alt som bygger egne redirect-URL-er fra Request.Host, inkludert SMART-callbacken.
  • Oppstartsrekkefølge: containere, SMART-mock, så appen.
  • Én app om gangen på port 5005 i localtests HTTP-modus.
  • Podman-maskinen stopper mellom økter: podman machine start, så start containerne på nytt.

SMART og auth

  • Både hemmelighet og nøkkelsti satt: private_key_jwt vinner stille. Test én ting om gangen.
  • Lang state: en for lang state-parameter kan gi 404 eller 500 hos Epic fordi URL-en blir for lang.
  • Epic og scopes: be bare om scopes appen er registrert for, i riktig stil (.read/.write for «v1»).

Altinn Studio-skjema

  • 403 ved instansiering: policy.xml må bruke [ORG]/[APP]-plassholderne; hardkodede, store bokstaver feiler fordi sammenligningen er case-sensitiv.
  • 500 ved skjema-henting: appen trenger en JSON Schema-fil for datamodellen.
  • Sitter fast på side 1: flersidige skjema får ikke navigasjonsknapper automatisk — legg NavigationButtons eksplisitt på hver side.
  • Etiketter forsvinner i Grid: komponenter inni et Grid viser ikke tittel og beskrivelse. Bruk labelFrom for tekstfelt; for avkryssingslister fant vi ingen løsning, så de ligger i vanlig rekkefølge.
  • Avkrysning uten tittel: en Checkboxes-gruppe trenger en ikke-tom tittel for å vises i det hele tatt.
  • Duplisert innhold i oppsummeringen: Summary2 med mål layoutSet tar med siden den selv står på. Bruk ett Summary2 per side i stedet.

Arbeidsflyt

Slik jobber vi

  1. 1

    Én gren per endring

    Lag en gren, commit, push og åpne en pull request mot main. Ikke jobb direkte på main.

  2. 2

    Slå sammen, og rydd

    PR-er slås sammen med en vanlig merge-commit og grenen slettes etterpå, slik at historikken viser at grenen er ferdig.

  3. 3

    Dokumentasjon er en del av endringen

    Endrer du docs/*.md, kjør docs/generate-samlet-dokumentasjon.ps1 og ta med den genererte DOKUMENTASJON-KOMPLETT.md. Rediger aldri samlefilen direkte.

  4. 4

    Nettstedet

    Endringer i site/ får en forhåndsvisning per PR og publiseres til GitHub Pages når PR-en slås sammen. Nettstedet er ferdig statisk HTML — ingen byggesteg.

  5. 5

    Hemmeligheter og pasientdata

    Aldri ekte pasientdata, aldri hemmeligheter. Bruk syntetiske testpersoner (Tenor) og lokale filer.

CI bygger src/App.sln og kjører dotnet test på Windows, macOS og Linux for hver PR — men det finnes ingen testprosjekter ennå, så grønn bygging betyr bare at det kompilerer.
